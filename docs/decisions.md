# orch mobile: prototype decisions (M0)

Status: converged 10 Oct 2026 from two independent proposals ([Claude](proposals/claude.md),
[Codex](proposals/codex.md)), then challenged by Codex ([challenge-codex.md](challenge-codex.md): all ten points accepted and folded in). Scope: the simulated prototype (P4 started early,
owner-approved). Where this file and a proposal differ, this file wins. Spec gaps found are in [gaps.md](gaps.md).

## Principles

- **P1. The fake sits at the relay wire.** Demo and tests run the real client stack (protocol v2 suite 2 bytes,
  real P-256 crypto, real pairing, sealing, epochs, push sealing) against an in-process FakeRelay, FakeHost and
  FakePrimary. Swapping in an HTTPS transport later changes nothing above `RelayTransport`. Faking at screen or
  repository level is rejected: pairing, epochs and push would go untested until the real relay exists.
- **P2. The fakes are held to the vectors too.** FakeHost/FakePrimary pass the host-side protocol vectors
  (`host_cases`, `cert_request`, `wk_grants`, member lists, push) so app and fake cannot be wrong together.
- **P3. Demo is a separate realm.** Own storage root, keychain prefix and relay host `relay.demo.invalid`, a
  persistent violet "Demo" marker, real transport never reachable from Demo. Leaving Demo wipes the realm.
  Demo certification is never security evidence. Enforced, not just named (challenge C1): synthetic authority
  keys (FakePrimary `PK`, FakeHost `WSK`/`WXK`) are generated fresh per Demo install/reset, kept only in
  backup-excluded Demo storage and erased on exit; no vector scalars or Python reference in shipped code;
  every shared record, route, job, keychain item and notification id is keyed by `(realm, ws, generation)`;
  FakePrimary is constructible only with Demo-scoped stores and the in-process transport; external origins and
  cross-realm links are rejected before any request; real `PK`/recovery material is never imported into Demo.
  Release-build negative tests cover real-transport reachability, live-key lookup, cert reuse and reset scope.
- **P4. D45–D49 override stale prose.** On the iPhone, D49: the device key signs whenever the phone is unlocked
  (Secure Enclave, `WhenPasscodeSetThisDeviceOnly`, no `.userPresence`). Explicit human confirmation in the
  UI stays: the sign sheet shows the exact text before "Sign and send".
- **P5. No silent workarounds.** Where the spec or protocol has no contract for the phone, the code uses a
  provisional, versioned adapter (`host-api v0`) and the gap goes into `gaps.md`.

| A15 | **Membership and rotation (P3-D6/D7).** Member lists carry `persons`, a `person_id` per member and (Q10, A16) `wk_commit`; the phone parses them strictly and only ever raises its epoch from a verified list (forward jumps allowed). The host publishes a list, every member's grant and optional card-key wraps in **one** `PUT /v2/workspaces/{ws}/membership` under its holder generation: it persists `WK_{e+1}` and the exact sealed body before the first send, resends those bytes (never reseals) while the outcome is open, and reconciles a `stale_list` after a lost reply with `GET members`. A refused body burns its epoch (A16): its key is retained but never activated or resealed, and the next rotation goes above it; there is no rotation-abandon route. Every W(g) write (membership, card, card-keys, pairing answers, cert requests) needs the strict holder lease (`Orch-Holder`; fenced without it, orch-29 Q9). Rotation invariants I1–I7 are restated in `FakeHostBridge.swift`. The phone keeps the head of the last verified list (`list_seq`, epoch, digest, member set) and refuses rollback, same-`list_seq` conflicts, a falling epoch, a removal without an epoch bump and a listed person without a member device; the join records its verified list as the head. | protocol-v2 §7.2, §19.2, §19.7 |
| A16 | **One WK per epoch, ever (orch-29 Q10, decided).** `member_list` carries the required `wk_commit = b64u(H("orch/v2/wk-commit|" ‖ workspace_id ‖ u32(epoch) ‖ WK))` (part of the exact field set). The phone seals (bridge and Drop) only under a key in custody that the **head** list's `wk_commit` commits, at the head list's epoch; mismatch or a missing list/grant blocks sending (`no_key`), never a fallback. Reads accept any WSK-verified grant, checked against `wk_commit` when a list for that epoch is held; a held commitment decides which key an epoch keeps. Device rules G2b D1–D4 (orch-relay 491b500, vectors `member_list_snapshots`, run through `WorkspaceSession`): the head's own `list_seq` with the same `cj(o)` is a no-op (signatures never compared), with other content `conflicting_snapshot` even if its `wk_commit` differs, and that alarm does not block sealing; otherwise two verified lists at one epoch with different `wk_commit` raise the local alarm `wk_commit_conflict` BEFORE the `stale_list` check (a lower `list_seq` with another commitment raises it too) and stop sealing at that epoch only, until a verified list at a higher epoch arrives (`sealing_blocked`, migration 13). While it blocks the head epoch every seal throws `wk_commit_conflict` (never "no key, retry later"); the App reads it at launch and shows a key alarm (workspace header, answer block, review sheet, new ticket, Drop) whose way out is removing the workspace and pairing again, unless the host's next rotation lifts it. Reads (D4) refuse an epoch above the head, or any epoch before a first verified list, with the local `future_epoch`. A grant the held list does not commit is refused (`wkCommitMismatch`) and surfaced the same way. When no committed key is usable, a send does ONE bounded list + grants fetch and retries once. Migration 12 drops the pre-Q10 head (no `wk_commit`; its digest would make the host's re-issued list a permanent `conflicting_snapshot`): the next verified list is accepted as a first list, never below the confirmed epoch. `conflicting_snapshot` still compares parsed content. The phone's `persons` check is one-way (each listed person has a member device); certificates of other members are the relay's (check 8, gap 27). Relay (FakeRelay `checkSequence`, list rules before any grant check): first list `1 ≤ epoch ≤ 2^16`, any `list_seq ≥ 1`; then `prev ≤ epoch ≤ prev + 2^16`, a removal needs `epoch > prev`, the same epoch needs the same `wk_commit` (409 `wk_commit_changed`; a held row without `wk_commit` counts as another commitment: no legacy skip, the host recovers by rotating). Host: never reseal at a refused epoch; keep its key retained (answers §8.5 `stale_epoch` for a pinned phone); raise the `list_seq` floor to the refused `list_seq` and the epoch floor to its epoch, rotate at floor + 1; `stale_card`/`wrap_conflict` resend the same signed list with fixed wraps (nothing burned); any refused same-epoch body that carried current-`WK` grants to a non-member forces a rotation. Every definite refusal burns its epoch, `bad_epoch` included (the relay saw the grants). Liveness (orch-29): the next rotation goes to `min(EHW + 1, committed + 2^16)` (EHW: the highest epoch ever sealed, committed or burned); when that clamp blocks a rotation the host raises a publication alarm and keeps the gate up, sending nothing. Additionally `bad_epoch` is not counted toward a burn limit of 8 refusals in a row, after which the host also alarms and stops. Vectors: orch-relay d3816ea (G2b merged at 491b500; `wk_commit`, `member_lists`, `member_list_snapshots`, HTTP fixtures pinned by the relay's MANIFEST.json revision 5; Q11 `p3.restore` and two bridge cases pending). | interim "replace an unconfirmed key" rule; keeping candidate keys per epoch |

## Provisional answers to owner questions (owner may override)

- D-1 Keep device keys and cert after leaving the last workspace; "Reset this iPhone" wipes them.
- D-2 The phone is never the primary device in P4. (PR4 adds the primary's relay client calls, D(p) cert-request
  poll, challenge and PK-signed rejection, for FakePrimary and a later primary phone; the shipped app does not act as one.)
- D-7 (PR4, amended by P3-D28 / orch-relay 04da0e7) A pairing ends as "Denied by the owner" (`pair.deniedByOwner`) only for a
  long-form `rejected` whose PK-signed `cert_rejection` passes all seven §8.3 checks for this attempt (pk_pin, signature,
  workspace and person, own device and dk_hash, attempt and offer, the accepted challenge's request id, expiry), attributed to
  the pinned owner key, never to `primary_label`. Anything else is the unattributed "The pairing was refused"; a rejection naming
  a foreign device raises the alarm. An uncertified phone uses fresh keys per attempt; join is gated by the `approved` anchor.
- D-3 (amended 15 Oct 2026, owner decision) The QR carries `orch://pair?relay=<origin>#v2.…` (the relay origin is always
  explicit; an `orch://` link without exactly one `relay` parameter is rejected). There are no universal links yet, so a
  pairing invitation arrives by QR or paste only, and a pasted `https://<relay>/app/pair#v2.…` link is accepted too.
  Mitigations for the custom scheme (any app can register it, and a link can be opened by anything): (1) the in-app scanner
  is the primary path (the system camera would hand the link to whatever claims `orch://`); (2) an `orch://` open ALWAYS lands
  on a review screen showing the reviewed origin read-only (ASCII/punycode), never connects by itself and never silently
  leaves Demo (while Demo is active the link is held in memory and the person is offered "Leave Demo and pair your Mac" with
  a destructive confirmation); (3) the origin must be `https` (no http loopback in the app; a shipped build cannot reach
  plaintext), one relay origin and one owner per Live install, and a different origin is refused before any network access;
  (4) the pairing itself still needs the Mac's comparison code approval, so an opened link alone cannot add anything.
- D-4 No `apns-collapse-id` in the prototype (S2's safer default); replacement via the NSE + delivered-item removal.
- D-5 Type scope (terminal) is out of P4 on the phone.
- D-6 Workspace display name comes from the signed card, opened with the device's sealed `CK` via a provisional
  authenticated fetch (delegation, card signature, `sealed_hash`, `ck_commit` verified); `approved` is not
  silently extended. The client-hosted marker comes from `delegation.client_hosted` ("hosted by (unknown)" when
  no name); a nonempty `hosted_by` also shows it. Bridge-provided names are never trusted for identity.
- Native exceptions to protocol v2 (recorded in gaps.md, to be amended upstream): CryptoKit/Secure Enclave instead
  of browser primitives, suite 2 only, APNs instead of Web Push, no passkey registration in pairing (§8.3 step
  6.4) on the native app, links `/app/pair` canonical with `/pair` accepted as alias, local leave vs push
  unsubscribe vs `member_remove` (Operate) kept distinct. Pairing, grant, push and leave adapters are versioned
  like the host view API.
