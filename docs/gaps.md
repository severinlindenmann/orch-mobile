## M2 protocol ambiguities

Found while implementing `OrchProtocol` and `OrchPush` against `docs/protocol-v2.md` and `vectors_v2.json`. Each entry names the reading the code takes. No vector contradicts any of them; none is resolved by guessing silently.

- **JSON nesting depth (§2.3, "at most 16 levels").** Resolved upstream in orch-relay #32: the Python reference now counts the root as level 1, accepting 16 and refusing 17, as Swift always did. Vectors `strict_parse.depth_16`, `depth_17`, `depth_16_objects`, `depth_17_objects` cover it and run in `strictParseVectors`.
- **`device_id` that is not hex in a revocation (§6.2, §14).** Python compares the string with the certificate's `device_id` and answers `other_person`; Swift parses it as an id first and answers `malformed`. The protocol text should say which.
- **Revocation refusal order (§6.2, §14).** The reference answers `bad_signature` for a wrong field set. Swift answers `bad_signature` only when the signature fails, and `malformed` for wrong `v`/`suite`/`kind`, wrong field set, a `person_id` that is not the signer's, a reason outside the list or a non-integer `revoked_ms`. The reference should follow.
- **§2.5 cleaning.** `Cn` (unassigned) and Default_Ignorable_Code_Point depend on the Unicode version of the Swift runtime. The reference uses a fixed range table. They can differ for code points added later.
- **§9 drop reasons.** The text names steps, the vectors name reasons (`size`, `shape`, `no_key`, `tag`, `signature`, `payload`, `stale`, `replay`). Swift maps "inner is not exactly {p, sig}" (and an undecodable `sig`) to `tag` as step 3 says (the reference says `payload` for the key set), a non-integer `epoch` to `shape`, and a negative or out-of-range integer `epoch` to `no_key`.
- **§9 replay state and the clock.** The text keeps "the highest `ts_ms` shown per (ws, id)" and a 24 h window against the local clock, but not what happens to the table. A clock wound back after pruning would make an old push shown again. Swift also keeps `maxShownTs`, the highest `ts_ms` actually shown (host time under the WSK signature, never the local clock). The lower bound is `max(now, maxShownTs) - 24 h` and entries older than `maxShownTs - 24 h` are pruned, so a wrong local clock can neither stale genuine pushes for long (the mark does not move when nothing is shown) nor resurrect a pushed entry. A push shown with `ts_ms` up to `now + 300 s` does move the mark; the protocol should say that this is accepted.
- **§13 `content_hash` in the decision signature.** The signature covers the `content_hash` as sent (b64u of 32 bytes), not a recomputation from the question. Signing and verifying use the same field values, as the reference does.
- **§1.2 / §2.3 and `-0`.** Not mentioned. Swift accepts `-0` and canonicalises it to `0`, as Python does.
- **§2.3 string comparison.** The protocol compares strings as code points or bytes. Swift's `==` is canonical equivalence (U+212A equals "K"). All protocol field checks in Swift compare UTF-8 bytes; a note in §2.3 would help other implementers.
- **Parser differential on object keys.** The Python reference compares keys by code point; Swift `String`, `Set` and `Dictionary` equality is canonical equivalence. Parsed objects cannot carry non-ASCII keys (both parsers reject them), and the Swift field-set checks additionally require ASCII keys and compare bytes, so there is no remaining accepted-input difference. Differences in codes only: for a signed object whose `o` has a non-ASCII key built in code, Swift answers `malformed`, while the reference never gets that far (`cj` raises, so `verify_object` returns None and the caller answers `bad_signature`).

### Slice 0 additions

Found while implementing the bridge, card, member-list, grant, cert-request, relay-auth and Drop codecs. Each names the reading the code takes.

- **Hosted marker for an empty `hosted_by` (§7.1 versus host-api §3).** The reference shows the marker when `hosted_by` is not null (an empty string included, named "(unknown)"). host-api v0 says "nonempty hosted_by". Swift follows the reference and protocol text ("a host can only add the warning"). Needs one line in §7.1.
- **Card `issued_ms` and `list_seq` ranges (§7.1, §7.2).** Not bounded in the text. Swift requires `issued_ms >= 0` on a card and any integer for `list_seq` (as the reference), and caps `card_seq`, `wxk_version`, `epoch` and wrap `version` to `1 ... 2^32-1` because they are written as `u32` in AADs.
- **Relay URL (§7.1).** The reference pattern accepts ports up to `:99999`, empty labels (`a..b`) and numeric hosts (`2130706433`, `0x7f000001`, `1.2.3.4`). Swift requires a port in 1 to 65535, no empty label, and applies the WHATWG "ends in a number" rule: the LAST label must not be all digits or a `0x` hex number (that is what makes a URL parser read the host as IPv4: `2130706433`, `0x7f000001`, `1.2.3.4`, `127.1`, `0177.0.0.1`). Other labels may look numeric (`123.example.com`, `0xdead.example.com` are DNS names). Punycode (`xn--`) labels are accepted and a UI must show the ASCII host, never an IDN-decoded one. The spec should state these rules.
- **Delegation and other signed objects with a wrong `v`/`suite`/`kind` (§2.4).** The reference answers `bad_signature` (verify_object returns None). Swift's `SignedObject.verify` throws `malformed` for these, and `WorkspaceDelegation`, `MemberList`, `WKGrant`, `CertRequest` and `DropDescriptor` map every failure of that step to `bad_signature` to match the vectors; `Revocation` keeps `malformed` (see above). The text of §2.4 should pick one.
- **Cert request, shape errors after the signature (§8.4 step 2).** The reference raises `KeyError` on a missing field. Swift answers `malformed` after the signature check and before the workspace and addressee checks. The `label` text is not cleaned by the primary (the host cleaned it at pairing, §2.5); a primary that shows it should still treat it as untrusted text.
- **Challenge issuance (§8.4 step 3).** The reference lets the primary issue a second challenge for the same request (it overwrites). Swift refuses (`replayed`) so the code cannot change under the human, and builds the challenge only from the stored request. It also refuses a certificate whose signer is not the request's person (`other_person`), and any scope list that is not a non-empty prefix of the four scopes (`scope_exceeded`), so a primary can never produce a drop-scoped certificate here.
- **Device response check (§8.8).** Two points the text leaves open. (1) The reference lets a second `stale_timestamp` refusal for a rid that already adopted an offset skip the time window check (the `if/elif`). Swift applies the normal window check to it, and retires a rid once its `last` chunk is accepted, so nothing is accepted after `last` (the reference keeps the rid pending). (2) A pending epoch for which the device holds no `WK` is a new drop reason `no_key`; the reference raises `KeyError`.
- **Sealed WK (§7.3).** The reference returns `tag` as a refusal code for a grant that fails to open. `tag` is not a §14 code; Swift throws `authenticationFailed` (a crypto failure, not a refusal) and `malformed` for a key that is not 32 bytes.
- **Drop (§10.2 to 10.4).** `meta` is typed as `{name, mime, size, transcript}` exactly, as in the vector; the protocol text lists the fields without saying they are exhaustive. Descriptor `recipients` must be hex ids (the reference only checks sortedness). `DropDocument.checkPut` additionally refuses a non-zero `current` with no head. The relay's claim check reads `workspace_id` before the signature (to find the card) and answers `not_eligible` for an unknown workspace; §10.5 lists `bad_signature` first.
- **Input caps (all parsers).** The protocol caps only the envelope (1 MiB / 256 KiB), meta (64 KiB) and push (3 KiB). Swift also caps the sealed card part (64 KiB), the cert-request inner (4 KiB), drop metadata (64 KiB), a wrap (1 KiB), a member list (1024 members) and a blob in memory (256 MiB), and gives `StrictJSON.parse` a 1 MiB default cap. These are implementation limits, not wire rules.
- **Snapshots versus publication (§7.1, §7.2).** The "update rules" are what a relay applies when a host publishes. A phone fetches the current card and list: it may see the same one again (reconnect), may have missed rotations (`card_seq`, `wxk_version`, `epoch`, `list_seq` jump), and on a late join its first list is far along. Swift has `Card.checkRelayUpdate` / `MemberList.checkRelayUpdate` for the relay and `Card.checkSnapshot` / `MemberList.checkSnapshot` for devices (identity pins kept, identical and forward accepted, rollback and conflicting same-sequence content refused; the local code `conflicting_snapshot` is never on the wire). The protocol should say which side each rule binds. A phone does not hold other members' certificates (gap 27), so its list check cannot include the relay's per-member certificate and grant checks.
- **Drop chain identity (§10.6).** `parent_hash` alone does not stop a descriptor of another object or space from extending a chain, because `parent_hash` hashes only the parent. Proposed amendment: a relay on `PUT` and a reader along a chain MUST require `object_id`, `space_id`, `space_kind` and `object_kind` equal to the head's (to version 1's, for a reader). The reference has the same gap; Swift enforces it. Readers must also persist the highest version per document (§10.6); that state is a later slice.

### Slice 1 additions (relay model, for orch-relay P3 to agree)

Found while building the transport and FakeRelay, and while fixing review findings. These are the relay behaviours host-api v0 now assumes.

- **Revoked devices get no relay session (gap 24; owner's decision).** Login for a revoked device answers 403 `revoked` after the signature verifies (an unknown or wrongly signed identity still gets the same `bad_signature` as ever, so revocation is no oracle). Publishing a revocation ends the device's live sessions and drops its grants, card-key wraps and queued bridge requests in every workspace. A revocation record is a public PK-signed object, so `GET /mobile/host-api/0/devices/{device}/revocation` takes no session and answers 200 `{"host_api":0,"record":...}` or 404 `not_found`. The client fetches it on any unsigned `revoked` and verifies it against the pinned PK before wiping. host-api v0 section 3 says the same.
- **Challenge limits must be per address, not global.** A global cap on outstanding challenges (the fake keeps 1024) lets one address lock every other device out of login. The real relay should cap outstanding challenges per client address and answer 429 `rate_limited` with `Retry-After`; a global ceiling only as a last resort that sheds the oldest, never the new.
- **Rate windows must be pruned.** Per-address and per-workspace windows (pairing posts and polls, challenges, the session-less revocation route) must drop idle entries, or the table is itself an unbounded memory sink. The fake prunes on every request.
- **Verify against a dummy key for unknown identities.** Login for an unknown device or workspace id must run a signature verification against a fixed dummy key so timing matches the known-identity path, return the same `bad_signature`, and still consume the challenge (the fake already matches the answers, not the timing).
- **Revocation removes the device's footprint.** Besides sessions: grants, card-key wraps, request mailboxes, push registrations. The fake does all but push (not modelled yet).
- **Retention is by time, not by read.** Sealed bodies are kept 60 s from receipt (section 8.9); polling never extends that; a mailbox with no live body is deleted. The fake prunes on every request and exposes the retained size for tests.
- **Uploads re-check at write time.** A relay accepting a host's grant or card-key wrap must check, in the same step as the write (no suspension between), that the session, card, device certificate (owned by the card's owner, unexpired now, not revoked) and epoch still hold. Membership is deliberately not required at upload: section 7.2 puts grants before the list that names the device.
- **Envelope limits are for the whole envelope.** `maxRequest` (1 MiB) and `maxChunk` (256 KiB) bound the complete ORB2 bytes, header and signature included, as the device's section 8.8 size check does. The relay must use the same numbers or a chunk it queued would be dropped by every device.
- **Retry-After is delta-seconds.** The client reads it as a strict decimal and clamps it to 1 to 3600 seconds; an HTTP-date or anything else is ignored.

### M7 push additions (phone side)

Choices made while building the notification extension, replay store and push material. None is a protocol change.

- **Per-workspace replay state (host-api v0 slice 4).** `PushProcessor.ReplayState` is now `[ws: WorkspaceReplay]`: each workspace has its own `maxShownTs` and `lastShown`. The 24 h floor and the pruning use only that workspace's mark, so a high timestamp in A can neither suppress nor prune B. Persisted per `(realm, ws, generation)` in the push App Group (`state/<realm>/<ws>/replay.<generation>.json`, the directory `StoreLayout.pushStateDir` names, so wipe phase 3 already removes it). There was no persisted legacy table; `ReplayState.migrating(legacy:)` rebuilds per-workspace state from retained entries only and never copies a global mark.
- **A3 amendment: the extension links OrchCoordination.** A3 says the extension links only OrchPush and OrchProtocol, but A11 requires its replay write and handoff to run under `TombstoneCoordination.ifNotRemoved`. That type (with the atomic-write and flock helpers) now lives in its own Foundation-only module `OrchCoordination`, extracted from OrchStore (which re-exports it, so existing `import OrchStore` code keeps compiling; new extension code should import OrchCoordination). `scripts/check-extension-links.sh` allows `OrchNotify` exactly `OrchPush, OrchProtocol, OrchCoordination`; OrchStore (SQLite), custody, client and FakeHost are rejected, with negative tests. The share extension's `ifNotRemoved` user should switch to OrchCoordination too.
- **Lost or reset replay history never re-enables a shown push.** `WorkspaceReplay.notBeforeTs`: nothing at or below it is accepted. Corrupt state is moved aside inside the transaction (`replay.<g>.json.corrupt`) and replaced at once by a state with `notBeforeTs = max(floor, now)`; snapshot reads (`load`) never mutate. A content-free per-(realm, ws) floor file (`push/floor/<realm>/<ws>.json`, the highest `ts_ms` ever shown) lives OUTSIDE the wiped state directory, and a new generation (rejoin) starts above it. The only cost is that a genuine push with `ts_ms` at or below the floor is dropped once. The app's wipe can additionally call `ReplayStore.raiseFloor(workspace:to:)` with the wipe time.
- **Removal and ordering hold until the handler is called.** `PushHandler.finalize` runs immediately before the content handler, under the shared removal lock and the workspace's replay lock: a workspace wiped in between delivers generic text, and a question whose id has since been accepted with a NEWER `ts_ms` (its closure) delivers generic text instead of the stale question. The notification already handed to the OS cannot be recalled (A11's second cleanup pass covers it).
- **Expiry never waits.** `serviceExtensionTimeWillExpire` completes at once with generic text and no I/O; the `expired` marker is written best-effort (try-lock, no fsync) and only if the time limit won; processing runs on a background queue; a presentation arriving after completion is rejected. All in `PushDelivery`, covered by deterministic interleaving tests.
- **Threat-model note: the floor file survives a wipe.** `push/floor/<realm>/<ws>.json` is named by the workspace id and holds one timestamp. It outlives the workspace on purpose (it is what stops replay after a rejoin), so a reader of the App Group container learns that the workspace once existed and roughly when its last push was shown; no content, label, name or key. A corrupt floor file fails closed (treated as `now` and rewritten).
- **Handoff happens inside the locks.** `PushHandler.handoff` calls the completion while holding the shared removal lock and the workspace's replay lock (waits bounded, default 3 s, then generic text); the deadline path claims the completion with no lock at all, so it always wins when the locks are slow.
- **Bounded replay state (protocol section 9 does not bound it).** The table stores SHA-256(id), not the id; ids over 128 UTF-8 bytes are refused (`payload`); at most 512 ids per workspace within the 24 h window; a new id at the cap is refused with generic text, never by evicting (eviction would re-enable a replay). The protocol should state both limits.
- **Tap routing must never trust `userInfo`.** The extension sets `orch_key` and `orch_ws`, but a malicious relay can omit `mutable-content`, skip the extension and deliver any userInfo. On tap the app must treat them only as a lookup key into locally verified data (reverify, fetch authoritative state, then act; U10), never as an identity or an instruction.
- **Material and replay generation.** Push material carries the workspace generation; the extension passes it to `ifNotRemoved`. A state file of a newer generation than the material refuses the push (stale material after a rejoin). Material and state are separate, so material older than state is `droppedState`.
- **Timeout after the write (issue #8 A).** The replay timestamp is made durable before anything is shown. If the time limit fires afterwards, the user sees generic text and the push is a replay for good. This is intended (fail closed) and now covered by the generic-on-expiry rule.
- **Clock set back (issue #8 D).** Unchanged: the floor is `max(now, maxShownTs) - 24 h`, so rolling the clock back cannot re-show a pruned push; rolling it forward only makes genuine pushes `stale` until it returns (no sticky mark). A clock set forward by more than 24 h drops genuine pushes while it is wrong.
- **`join` is verified but shown as generic text (gap 13).** The extension cannot suppress a notification, so the OS shows the app-authored generic line.
- **Rejected and expired pushes show generic text.** `New activity in orch`, no sound, no thread, no userInfo: a documented native exception to section 9's "drop" (A12). The relay's alert, title, subtitle, sound, category, thread-id and userInfo are never read. Text from a signed payload (label, workspace name) has control, bidi and format characters stripped before display.
- **Invocation marker.** The extension writes `push/nse-marker.json` (counter, outcome enum, timestamp in ms) on every invocation. It holds no label, id, workspace id or name. It is the only accepted evidence that the extension ran.
- **simctl push and the extension (gap 32).** See the M7 report: whether `simctl push` launches the extension is recorded by the marker in `UITests/PushNSETests`, never assumed.

### Slice 2a additions (host bridge and WorkspaceSession; for the real host and for v1 to agree)

- **Persist the seq window and the rid store atomically together.** A host that restarts with the rid store but not the sequence window (or the reverse) is safe only for one of the two replay defences; one that loses both re-runs a replayed accepted request. A real host must commit both in the same transaction as the decision to run a request. The FakeHost tests spell out the four combinations.
- **A re-send is never re-signed (U8).** The device re-sends a stored envelope byte for byte only while the host surely still holds the rid record: 900 s minus a 600 s safety margin, measured as the larger of the monotonic and the persisted wall age. A refusal that would need a new seq, timestamp or epoch (`stale_sequence`, `stale_timestamp`, `stale_epoch`), `already_done(unknown)` and the end of the window all make the request durably `uncertain` (immutable logical id and signed plaintext kept) until reconciliation resolves it. New attempts after a refusal of a FIRST send are replaced atomically (insert new, delete old, one transaction).
- **After the handler the host re-checks epoch, revocation and membership** and answers `already_done(unknown)` if any changed; rotation ends open streams with `LAST|REFUSAL` `stale_epoch`; a revocation op for a member runs the full rotation before replying. The protocol text (8.5, 6.2) implies this; it should say the check happens after the handler.
- **A grant ahead of its list is stored but not used.** The device raises its current epoch only to an epoch confirmed by the verified member list or by a verified higher `stale_epoch` refusal (section 7.2 order uploads grants first).
- **Pin-failure counter is consecutive.** Three host-signature failures in a row mean pair again; a verified response resets it. The v1 behaviour (cumulative or consecutive) needs confirming; consecutive avoids a permanent lockout from three unrelated corrupt chunks over a device's lifetime.
- **HostBridgeCore prunes expired rid records** on every check; the quotas count live records only.
- **Rotation gates all data sealing.** Public and revocation-triggered rotations enter one shared gate before the first suspension. After a non-stream handler returns during publication, the host refuses with `already_done(unknown)`; otherwise it waits as needed and re-checks epoch, revocation and membership. A durable `rotationRequired` (also set before a revocation removes the member, cleared only after grants, list and the new epoch are installed) blocks data replies and replay while publication is pending. Failed publication retains its requested roster and relay context for retry on the next pump or resubmitted revocation. The one exemption is the revocation op's own non-sensitive `{"revoked":true}` reply, sealed under the request's epoch as section 8.5 requires.

## Slice 2a rotation amendment

Fake-only until the protocol is amended: failed rotation attempts use skip-epoch recovery after authenticated retirement. The provisional host-api v0 route is `POST /mobile/host-api/0/workspaces/{ws}/rotation-abandon`, with the workspace bearer, the usual host-api version header, and a WSK-signed `{o, sig}` envelope whose body is `{kind:"rotation_abandon", workspace_id, epoch}`. The local OrchFakeHost label is `orch.host-api.0.rotation_abandon`; the signature covers that label followed by canonical JSON of the body. OrchProtocol signed-object vectors are unchanged.

The relay accepts only `epoch == max(current list epoch, retired watermark)` or exactly one greater, rejects unsigned/wrong-key bodies and wrong workspace credentials, advances the retired watermark, and deletes that epoch's grants. Repeating retirement at the watermark is idempotent. Lists and grants cannot reuse retired epochs; a forward list jump requires the retired watermark and advances at most one beyond it. `checkRelayUpdate(..., abandonedThrough:)` is provisional. The host retains unacknowledged retirement and retries it with current credentials before allocating another epoch, including when the acknowledgement was lost. Publication failures retain pending work and the gate; retries use capped exponential monotonic backoff (100 ms to 1.6 s).

The host checks its roster before publishing the list. A removal observed after the list commits causes a follow-up rotation while keeping the gate raised and preserving the committed epoch's grants; it does not retire that current list epoch. Pending work uses refreshed credentials supplied by pump or resubmission. Phones already accept forward epoch jumps. Protocol-v2 section 7.2, the Python reference, and a conformance vector must change before the real relay relies on this amendment.

- **Rotation gates all data sealing.** After a handler returns, the host waits for any rotation in progress and re-checks epoch, revocation and membership; a durable `rotationRequired` (set before a revocation removes the member, cleared only after grants, list and the new epoch are installed) blocks every data reply and is retried on the next pump or resubmitted revocation. The one exemption is the revocation op's own non-sensitive `{"revoked":true}` reply, sealed under the request's epoch as section 8.5 requires.

### Slice 2b additions (pairing, verified identity)

Found while building the pairing coordinator, FakeHost/FakePrimary pairing and the join checks. Each names the reading the code takes.

- **Host to primary queues have no wire form (gap 22, §8.4).** The host posts a `cert_request` "to the relay's queue for `(person_id, primary_device_id)`", the primary posts its `cert_challenge` "to the queue for `(workspace_id, request_id)`", and the host "polls the directory for the certificate". No route, authentication or retention is given for any of the three. FakeRelay keeps them as internals (host workspace session posts requests, the unauthenticated-by-session primary posts a PK-signed challenge, the host reads it by request id) and expires them with the request plus a 60 s grace (the same constant host-api section 6 states; FakeRelay's `queueGraceMs`). P3 must define them, including who may read a challenge: the phone gets it only through the host's `cert_pending` answer, so the relay need not serve it to anyone but the host.
- **Primary rejection reaches the host only by a v0 invention (host-api section 6; gap 22).** §8.4 says a human who rejects "closes the request"; nothing tells the host, so the host would sit in `cert_pending` for 10 minutes and then answer `expired`. v0 lets the primary post a rejection that the host reads and turns into `rejected`. The phone sees `rejected`, which is indistinguishable from a host rejection. The fake's rejection marker is unauthenticated; a real one must be a PK-signed object (`cert_rejection` over `request_id`, `workspace_id`, `person_id`) that the relay verifies against the owner key before it shows it to the host, or any party that learns a request id could cancel a pairing. Needs P2/P3 agreement or the phone must treat `expired` as the only outcome.
- **The pending state has no host-side deadline (§8.3).** `cert_pending` has its own 10 minutes, the offer has 10 minutes, but a `pending` pairing that the host's human never decides has no stated end. The fake keeps it until the host acts; the phone enforces its own 10-minute cap from link parse (host-api section 6), so a host whose human decides later answers a phone that has already erased the pairing. The host should state one (the offer's own 10 minutes is the natural bound) and answer `expired` with it.
- **`pair` resend after the state moved on (§8.3 step 3.2).** "A resend by the device that holds the pending pairing, with the same two keys, is answered `pending` again." The text does not say what a resend gets once the pairing is `cert_pending` or `approved`. The fake answers `pending` (as written). A phone only sends `pair` until a `pending` was accepted (a verified `stale_timestamp` refusal, which also teaches it the host's key, is answered with another `pair`, never a `pair_status`) and ignores answers to any rid but the one in flight, so a stale duplicate cannot move it; but the host should say whether a resend gets the CURRENT state (the phone would then accept a later state straight after a lost first answer, which the coordinator today treats as a regression alarm).
- **No initial answer within 60 s is `linkUsed`, even when the cause is the relay (§8.3 step 4, v1 text).** A 429 with a long `Retry-After`, or a lossy network, in the first minute ends the pairing with "this link was used by someone else". That follows the text; the message is wrong for a relay fault. The text should allow an inconclusive-connection message ("could not reach the relay; the link may or may not have been used") when the silence may be a relay fault (a 429, repeated transport errors) instead of asserting that someone else used the link; the coordinator keeps `linkUsed` until then. The 60 s deadline is never extended by a longer Retry-After: `run()` schedules the earliest deadline. After the first verified answer the 60 s rule no longer applies and transport trouble backs off 20/40/60 s without ending the pairing.
- **Regression and substitution alarms are the coordinator's, not the protocol's (host-api section 6).** §8.3/§8.4 define the alarm only for foreign keys in `pending` and in the challenge (`not_my_key`). "A later answer may not move back" (pending after cert_pending, a withdrawn challenge, a changed `sas_nonce` or challenge) is host-api v0 behaviour. The relay can replay old chunks inside the 60 s retention; the phone answers only the rid in flight, so replay alone cannot cause an alarm.
- **Label shown to the person.** `primary_label` is host-supplied text and §2.5 says the host cleans it, but the phone must not trust that. Both the alarm instruction and the cert-pending screens (`waitingPrimary`, `comparingPrimary`) show it only when it is at most 40 scalars of letters, digits, space and `-_.'` (`PairingAlarm.safeLabel`); otherwise "your primary device".
- **Stored certificate (D-1).** After a join the phone keeps `{cert, pk_pub}` under the `device.cert` secret. The certificate is public data but the pin of its owner is not recoverable from it, so the owner key is stored beside it. A later link whose `pk_pin` is not the stored owner's is refused locally as "belongs to someone else" before anything is sent (§8.3 step 2: "the phone shows ... and sends nothing"). Two people's certificates on one device (gap 28) are not supported.
- **Order of the join checks.** Host-api section 3 lists them; the code runs card (PK delegation against the pinned owner, pinned WSK, workspace, `relay_url` byte-equal to the reviewed origin, first-contact snapshot), card-key target and `ck_commit`, member list (pinned WSK, this device with exactly the approved scopes, epoch not below the approved one), then grants (the highest verified grant must be the list's epoch). A card that is fetched before its wrap is published, or a grant for an older epoch than the list, keeps the phone in `joining` for up to 60 s; a wrap that opens to a key failing `ck_commit` fails the join for good. A relay that serves grants only to listed members means a host that "forgets" to list the device is seen as a join timeout, not a scope failure.
- **Join retries end.** A join that cannot complete for 60 s is `failed(.joiningTimedOut)`, retryable with `retryJoin()` until 10 minutes after the first `approved` (or the certificate's own expiry if earlier); then everything is erased (`expired(.afterApproval)`). `run()` does not spin in the timed-out state; it waits for the retry, a cancel or that end. The pairing secret `S` is erased from the stored record the moment `approved` is pinned (the join does not use it). The spec has no word on how long an approved-but-unfinished join may linger; this is the v0 choice.
- **Crash recovery.** The coordinator's `recover()` (run it at launch before `resume`) removes vault items of workspaces that are neither committed nor pending, a committed workspace's stale `pairing` record, pending rows without a record, directories nothing owns, and finishes erasures that failed (`cleanup` rows) and alarm leftovers. Device keys created by a pairing that crashed before its first row cannot be told from an identity the user already had, so they stay.
- **Not in this slice: push publication vs §6 `ready`.** Host-api section 6 puts the push keys (`K_push`, the pinned `wsk_pub`, the card name in the push group) in the `ready` step; the coordinator hands back the session and commits the profile but publishes none of it, because the push group and registration belong to slice 4. A UI that treats `ready` as "notifications work" is wrong until then; notification permission is the UI's. The coordinator hands back the `WorkspaceSession` and commits `workspace_profiles` (name, hosted marker, pins, accepted card) in the index.

Physical-iPhone sharing from Photos, Files and Safari stays on the release checklist.

## Slice 5 additions

- **Workspace Drop scope (provisional v0):** `look` permits listing, downloading and `drop_rewrap`; `operate` permits device-authored PUT and explicit `drop_claim`. The client verifies the pinned workspace WSK or a caller-supplied, owner-verified device certificate plus the signed current member list. There is no certificate-directory route in v0: unknown device authors fail closed. Removed authors likewise fail closed until a historical authorization-proof contract exists. This slice implements workspace spaces; personal/shared-space composition and scoped-agent enrollment remain outside the mobile adapter.
- **Upload packaging and limits:** all objects, including immutable files, use `PUT /drop/{id}/versions`. Absent objects have current=0 and require `If-Match: 0` (the existing upstream amendment proposal). Protocol errors retain §14 bodies without `host_api`; successful adapter wrappers carry `host_api:0`. `content_len` counts ciphertext bytes. Phone plaintext is capped at 25 MiB, metadata at 64 KiB, wraps and chains at 1,024 entries, and upload JSON at 36 MiB. Fake storage defaults to 1,024 retained versions / 100 MiB ciphertext. Files require a future expiry at most seven days away; expired objects disappear from access and reclaim quota. Downloads use object/version filenames, never metadata paths.
- **Durability and rollback:** exact ciphertext upload bodies are recorded in workspace SQLite before PUT. A 201, a lost response, or a 409 is reconciled by fetching and byte-comparing the signed descriptor and ciphertext. Conflicting content never triggers resealing or an automatic merge. The reader persists the highest version **and head hash**, checks the entire chain from version 1, and rejects a lower latest or a chain that does not extend that persisted head. `resumeUploads` returns an independent result for every pending row and continues after failures. `failedUploads` lists persisted failure reasons after restart. Durable `done=2` marks terminal conflicts/expired/rejected uploads; `done=0` remains retryable and `done=1` is confirmed. `retryUpload`/`discardUpload` explicitly resolve terminal rows; `discardShareJob` also removes abandoned staging plaintext and item mappings. Confirmed records remain available to share-job recovery.
- **Wraps and host authority:** phone sends carry fresh per-version DEKs wrapped to WXK, the sender device, and current WK (the §10.3 member-writer wrap, enabling existing peers to read). Missing epoch keys invoke the exact `drop_rewrap` bridge operation; the host opens its old WK wrap and uploads a current-epoch WK wrap. WXK is the fallback for newly addressed content. Unclaimed inbox objects require explicit `drop_claim` with operate scope. `drop_rewrap` rejects an unclaimed inbox; a previously claimed inbox gets a new current-WK wrap without submitting another claim. Wrap read-back includes nullable `claimed_by`; download refuses an unclaimed inbox even if it contains a usable wrap. The phone never obtains a WSK or a historical WK grant through this path.
- **Share import and removal:** a workspace SQLite ledger maps every staged job/item to a stable object ID before sealing. Concurrent imports of one job share a task; insert-or-load of the winning upload body is atomic in SQLite, and concurrent recovery shares each in-flight upload. Retry/restart uses the same persisted ciphertext unless the version slot is empty and its WK epoch is stale: then it decrypts locally and reseals with a fresh DEK at the signed current epoch. Send and retry check current signed membership and operate scope before PUT; newer lists require matching refreshed grants or refusal. Only when every item's upload has been read back successfully is staged plaintext removed. Destination realm/workspace/generation must match; no implicit redirect. Imported URLs remain literal text. Download publication takes the tombstone lock without waiting (`timeout:0`), writes atomically with Complete protection, and rechecks removal; wipe removes `files/`, uploads and rollback state with the workspace.
- **Demo compatibility:** `makeViewHosts` keeps the old `dropMetadata` property empty for the separate UI branch. The first bridge pump after enrollment uploads actual signed/encrypted fixtures: Laptop has readme, empty file, UTF-8 note and literal URL; Client VM has a WXK-addressed deployment file claimed through §10.5 and a two-version Runbook. Seed retries reuse their original ciphertext. `seedDrop` is also callable explicitly by integration tests; `DemoSetup.seedDropSending` uses the phone's DropService after pairing with operate scope, so the host never receives a device signing handle. No metadata-only file is presented as downloadable.

- **Verified metadata:** `downloadVerified` returns a Sendable `DropDownload` containing a URL and authenticated `DropMetadata` (name, MIME, plaintext size, transcript); the URL-only convenience API remains. DEKs stay private. Bad AEAD/DEK-commit candidates are skipped so a poisoned wrap cannot mask a later valid wrap.
- **F4 deferred — chain request amplification:** each list still verifies complete chains, up to 1,024 rows × 1,024 versions. A persistent descriptor cache plus a per-call fetch budget needs an incremental chain acceptance transaction and a pagination/partial-list contract; simply trusting cached author checks would bypass current-member fail-closed authorization. This fix round preserves complete verification; the hostile-relay request amplification remains open.
- **F6 deferred — response buffering:** JSON/blob limits still apply after a `WireReply` has buffered its body. A transport-level streaming response budget needs a bounded sender contract (including cancellation and Content-Length handling) across live and in-process senders; parser limits alone cannot fix this. Add per-route limits, with signed content length plus framing slack for blobs, before live Drop rollout.
- **Residual rotation race (security review, low):** a rotation landing between `performUpload`'s membership check and the PUT can still commit content under the previous WK, because the relay does not check epochs on PUT; a relay serving a stale signed member list has the same effect. Needs a relay-side check (reject a PUT whose member WK wrap is older than the current list epoch) or a list freshness field — upstream protocol item.
- **Read availability during grant lag (low):** read paths refresh membership too; a newer list arriving before this device's grant makes `list`/`download` fail with `unavailableKey` until the grant lands. Consider relaxing epoch equality for look-only reads.
- **Real host must gate rewrap on `claimed_by`:** in the fake only the relay's `putRewrap` refuses an unclaimed inbox; `FakeHost.rewrapDrop` does not check claim state itself. The real host must check it (defence in depth).
- **F7 core done; app foreground wiring pending (after #31) — plaintext expiry:** `drop_heads` persists the downloaded version, signed object expiry, and local `downloaded_at`. Plaintext expires at the earlier of the signed expiry (if any) and 7 days after download, including documents with null `expires_ms`; withholding newer versions cannot extend that local deadline. Re-download after purge starts a new local retention period without clearing the verified head. Drop list/download and the public foreground hook `purgeExpiredDownloads()` remove expired files, superseded versions, and untracked legacy files and downloads without a recorded download time. Verified newer heads purge older plaintext immediately. Publication checks the current head and expiry inside the same SQLite transaction used by cleanup, under the tombstone lock, and atomically replaces the file. HookGate/fake-clock tests cover signed expiry, the 7-day document cap, re-download, restart, newer versions, and preview publication races. Cleanup runs on these entry points; relay expiry alone does not delete local plaintext while the app is inactive.
