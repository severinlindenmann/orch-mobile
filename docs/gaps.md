# orch mobile: spec and protocol gaps

Status: M0, 10 Oct 2026. Merged and deduplicated from [proposals/claude.md §5](proposals/claude.md) (5.1, 5.2, 5.3)
and [proposals/codex.md §8](proposals/codex.md). Context: [decisions.md](decisions.md).

This list is input for two readers: the owner of the orch-core spec (and the protocol), and whoever does the real
relay and host integration. The prototype runs against a FakeRelay, FakeHost and FakePrimary, so it works around
each gap with a provisional choice. Every item names where it must be fixed. "Spec" is
`orch-core/docs/architecture/orch-v2.md`; "protocol" is `orch-relay/docs/protocol-v2.md`; "issue #n" is in
orch-mobile. Section references were checked against both files on 10 Oct 2026. Items resolved by the
"Provisional answers" in decisions.md are marked "provisionally decided: D-x"; the owner may still override them.

"Must be fixed by": spec text, protocol amendment, relay (P3), host (P2), orch-mobile.

## M2 protocol ambiguities

Found while implementing `OrchProtocol` and `OrchPush` against `docs/protocol-v2.md` and `vectors_v2.json`. Each entry names the reading the code takes. No vector contradicts any of them; none is resolved by guessing silently.

- **JSON nesting depth (§2.3, "at most 16 levels").** The Python reference (`_check_json`) counts depth from 0 and fails only when `depth > 16`, so it accepts 17 nested containers. Swift implements 16 container levels at most. The reference should change to `depth >= 16` (counting the current container). No vector covers it.
- **`device_id` that is not hex in a revocation (§6.2, §14).** Python compares the string with the certificate's `device_id` and answers `other_person`; Swift parses it as an id first and answers `malformed`. The protocol text should say which.
- **Revocation refusal order (§6.2, §14).** The reference answers `bad_signature` for a wrong field set. Swift answers `bad_signature` only when the signature fails, and `malformed` for wrong `v`/`suite`/`kind`, wrong field set, a `person_id` that is not the signer's, a reason outside the list or a non-integer `revoked_ms`. The reference should follow.
- **§2.5 cleaning.** `Cn` (unassigned) and Default_Ignorable_Code_Point depend on the Unicode version of the Swift runtime. The reference uses a fixed range table. They can differ for code points added later.
- **§9 drop reasons.** The text names steps, the vectors name reasons (`size`, `shape`, `no_key`, `tag`, `signature`, `payload`, `stale`, `replay`). Swift maps "inner is not exactly {p, sig}" (and an undecodable `sig`) to `tag` as step 3 says (the reference says `payload` for the key set), a non-integer `epoch` to `shape`, and a negative or out-of-range integer `epoch` to `no_key`.
- **§9 replay state and the clock.** The text keeps "the highest `ts_ms` shown per (ws, id)" and a 24 h window against the local clock, but not what happens to the table. A clock wound back after pruning would make an old push shown again. Swift also keeps `maxShownTs`, the highest `ts_ms` actually shown (host time under the WSK signature, never the local clock). The lower bound is `max(now, maxShownTs) - 24 h` and entries older than `maxShownTs - 24 h` are pruned, so a wrong local clock can neither stale genuine pushes for long (the mark does not move when nothing is shown) nor resurrect a pushed entry. A push shown with `ts_ms` up to `now + 300 s` does move the mark; the protocol should say that this is accepted.
- **§13 `content_hash` in the decision signature.** The signature covers the `content_hash` as sent (b64u of 32 bytes), not a recomputation from the question. Signing and verifying use the same field values, as the reference does.
- **§1.2 / §2.3 and `-0`.** Not mentioned. Swift accepts `-0` and canonicalises it to `0`, as Python does.
- **§2.3 string comparison.** The protocol compares strings as code points or bytes. Swift's `==` is canonical equivalence (U+212A equals "K"). All protocol field checks in Swift compare UTF-8 bytes; a note in §2.3 would help other implementers.
- **Parser differential on object keys.** The Python reference compares keys by code point; Swift `String`, `Set` and `Dictionary` equality is canonical equivalence. Parsed objects cannot carry non-ASCII keys (both parsers reject them), and the Swift field-set checks additionally require ASCII keys and compare bytes, so there is no remaining accepted-input difference. Differences in codes only: for a signed object whose `o` has a non-ASCII key built in code, Swift answers `malformed`, while the reference never gets that far (`cj` raises, so `verify_object` returns None and the caller answers `bad_signature`).

### Slice 0 additions

Found while implementing the bridge, card, member-list, grant, cert-request, relay-auth and Drop codecs. Each names the reading the code takes.

- **Hosted marker for an empty `hosted_by` (§7.1 versus host-api §3).** The reference shows the marker when `hosted_by` is not null (an empty string included, named "(unknown)"). host-api v0 says "nonempty hosted_by". Swift follows the reference and protocol text ("a host can only add the warning"). Needs one line in §7.1.
- **Card `issued_ms` and `list_seq` ranges (§7.1, §7.2).** Not bounded in the text. Swift requires `issued_ms >= 0` on a card and any integer for `list_seq` (as the reference), and caps `card_seq`, `wxk_version`, `epoch` and wrap `version` to `1 ... 2^32-1` because they are written as `u32` in AADs.
- **Relay URL (§7.1).** The reference pattern accepts ports up to `:99999`, empty labels (`a..b`) and numeric hosts (`2130706433`, `0x7f000001`, `1.2.3.4`). Swift requires a port in 1 to 65535, no empty label, and no all-digit or `0x`-hex label; punycode (`xn--`) labels are accepted and a UI must show the ASCII host, never an IDN-decoded one. The spec should state these rules.
- **Delegation and other signed objects with a wrong `v`/`suite`/`kind` (§2.4).** The reference answers `bad_signature` (verify_object returns None). Swift's `SignedObject.verify` throws `malformed` for these, and `WorkspaceDelegation`, `MemberList`, `WKGrant`, `CertRequest` and `DropDescriptor` map every failure of that step to `bad_signature` to match the vectors; `Revocation` keeps `malformed` (see above). The text of §2.4 should pick one.
- **Cert request, shape errors after the signature (§8.4 step 2).** The reference raises `KeyError` on a missing field. Swift answers `malformed` after the signature check and before the workspace and addressee checks. The `label` text is not cleaned by the primary (the host cleaned it at pairing, §2.5); a primary that shows it should still treat it as untrusted text.
- **Challenge issuance (§8.4 step 3).** The reference lets the primary issue a second challenge for the same request (it overwrites). Swift refuses (`replayed`) so the code cannot change under the human, and builds the challenge only from the stored request. It also refuses a certificate whose signer is not the request's person (`other_person`), and any scope list that is not a non-empty prefix of the four scopes (`scope_exceeded`), so a primary can never produce a drop-scoped certificate here.
- **Device response check (§8.8).** Two points the text leaves open. (1) The reference lets a second `stale_timestamp` refusal for a rid that already adopted an offset skip the time window check (the `if/elif`). Swift applies the normal window check to it, and retires a rid once its `last` chunk is accepted, so nothing is accepted after `last` (the reference keeps the rid pending). (2) A pending epoch for which the device holds no `WK` is a new drop reason `no_key`; the reference raises `KeyError`.
- **Sealed WK (§7.3).** The reference returns `tag` as a refusal code for a grant that fails to open. `tag` is not a §14 code; Swift throws `authenticationFailed` (a crypto failure, not a refusal) and `malformed` for a key that is not 32 bytes.
- **Drop (§10.2 to 10.4).** `meta` is typed as `{name, mime, size, transcript}` exactly, as in the vector; the protocol text lists the fields without saying they are exhaustive. Descriptor `recipients` must be hex ids (the reference only checks sortedness). `DropDocument.checkPut` additionally refuses a non-zero `current` with no head. The relay's claim check reads `workspace_id` before the signature (to find the card) and answers `not_eligible` for an unknown workspace; §10.5 lists `bad_signature` first.
- **Input caps (all parsers).** The protocol caps only the envelope (1 MiB / 256 KiB), meta (64 KiB) and push (3 KiB). Swift also caps the sealed card part (64 KiB), the cert-request inner (4 KiB), drop metadata (64 KiB), a wrap (1 KiB), a member list (1024 members) and a blob in memory (256 MiB), and gives `StrictJSON.parse` a 1 MiB default cap. These are implementation limits, not wire rules.
- **Snapshots versus publication (§7.1, §7.2).** The "update rules" are what a relay applies when a host publishes. A phone fetches the current card and list: it may see the same one again (reconnect), may have missed rotations (`card_seq`, `wxk_version`, `epoch`, `list_seq` jump), and on a late join its first list is far along. Swift has `Card.checkRelayUpdate` / `MemberList.checkRelayUpdate` for the relay and `Card.checkSnapshot` / `MemberList.checkSnapshot` for devices (identity pins kept, identical and forward accepted, rollback and conflicting same-sequence content refused; the local code `conflicting_snapshot` is never on the wire). The protocol should say which side each rule binds. A phone does not hold other members' certificates (gap 27), so its list check cannot include the relay's per-member certificate and grant checks.
- **Drop chain identity (§10.6).** `parent_hash` alone does not stop a descriptor of another object or space from extending a chain, because `parent_hash` hashes only the parent. Proposed amendment: a relay on `PUT` and a reader along a chain MUST require `object_id`, `space_id`, `space_kind` and `object_kind` equal to the head's (to version 1's, for a reader). The reference has the same gap; Swift enforces it. Readers must also persist the highest version per document (§10.6); that state is a later slice.
